# 渲染档位与性能（v2.0）

> 本文档回答四个问题：**有哪些档位、质量/速度/体积怎么权衡、快门与并行是怎么实现的、4K60 得要多大的机器。**
> 所有档位都是可选项 —— 不传任何新参数时走 `balanced`，行为等价于旧的 1080p30 默认。

相关入口：`scripts/render_video.mjs`（渲染器）、`scripts/blur_integrate.py`（快门积分器）、
`scripts/bench_render.py`（基准工装）。

---

## 0. 渲染通道：PNG / PNG-fast / JPEG（★ 渲染前必须问用户）

**通道 = 中间帧存成什么格式**，与最终编码质量（`--crf` / `--preset`）**解耦**：
换通道只换中间帧容器，不代表要降成片码率。

> **硬规则（SKILL.md 确认点 5）**：动手渲染之前，把下表摆给用户挑，**不许默认开工**；
> 选定值写进 `consent.json` 的 `render_channel`，由 `gate_check.py --phase render` 挡在渲染之前。
> 用户在打样阶段选定后可沿用同一轮；换通道/换档位要重新确认一次。

| 通道 | 参数 | 逐帧耗时（纯 CSS 图形 / 满幅照片） | 相对速度 | 画质 | 中间帧体积 | 适用 / 推荐 |
|---|---|---|---|---|---|---|
| **PNG**（默认） | 不带开关 | 45ms / **582ms** | ×1.0 | 逐像素无损 | 基准 | 只在像素级复现旧成片（`--profile legacy`）或 `master` 极限画质时用 |
| **PNG-fast** | `--png-fast` | — / 132ms | **×4.4** | **逐像素无损** | +22% | ★ **默认推荐**：无损且够快 |
| **JPEG q95** | `--jpeg --jpeg-quality 95` | — / 52ms | **×13** | PSNR 41.65dB（低于 x264 crf18 自身失真） | ~1/5 | 满幅照片 / 复杂合成 / 长片省磁盘 |
| **JPEG q82** | `--jpeg --jpeg-quality 82` | — / 41ms | **×14** | 略低，仍高于多数成片编码失真 | ~1/5 | 打样 / 迭代预览 |

**询问话术（照抄）**：

> 渲染通道你要哪条？① PNG（无损，最慢）② **PNG-fast（无损，快 4.4×，推荐）**
> ③ JPEG q95（快 13×、体积 1/5，肉眼无差）④ JPEG q82（最快，打样用）

**自动推荐口径**（给建议，但仍要用户点头）：

| 片子情况 | 建议通道 | 理由 |
|---|---|---|
| 帧里有满幅照片 / 重合成 | `--png-fast`；片长 >10 分钟或磁盘紧张 → `--jpeg --jpeg-quality 95` | PNG 在照片帧上是 582ms/帧，是最大的时间与磁盘黑洞 |
| 纯 CSS 图形帧 | 默认 PNG 或 `--png-fast` 都可 | 10× 差距只在照片帧上才出现 |
| 看节奏的打样 | `--profile draft`（档位内已含 `png-fast`）+ `--preview` | 不必额外指定通道 |
| 4K 终稿 | 必须 `--png-fast` 或 `--jpeg q95` | 4K 精细 PNG 单帧 2–6 MB，磁盘与编码都会被吃干 |

**为什么换通道是最大的提速杠杆**：中间帧编码在**浏览器进程内串行**，
`--concurrency` 完全无效（实测并发 1/3/6 路总吞吐 1.80 / 1.86 / 1.87 帧/秒）。
想快只有两条路 —— **换通道**，或 **`--workers` 真·多进程**。

JPEG q95 的失真已低于 x264 crf18 自身的失真，成片**看不出**；q82 更适合只作内部预览。

## 1. 档位表

`--profile` 给的是**成套预设**；任何显式开关（`--quality / --fps / --shutter / --workers / --crf / --preset`）
都会**覆盖**档位里的对应项。查看全部档位：

```bash
node <skill>/scripts/render_video.mjs . --list-profiles
```

| 档位 | 画质 | 帧率 | 快门 | 截图模式 | CRF / preset | workers | 用途 |
|---|---|---|---|---|---|---|---|
| `legacy` | 1080p | 项目 fps（默认 30） | 关 | `png`（无损精细） | 18 / medium | 0（单浏览器 + 场景级并发） | **逐位复现 v1.4.x 旧成片** |
| `draft` | 1080p | 30 | 关 | `png-fast` | 20 / veryfast | 6 | 打样 / 迭代，最快 |
| `balanced` | 1080p | 30 | 180° | `png-fast` | 18 / medium | 6 | **默认推荐**（质量/速度平衡） |
| `final` | 4K | 60 | 180° | `png-fast` | 16 / slow | 8 | 终稿（耗时约 1080p30 的 8–12×） |
| `master` | 4K | 60 | 180° | `png`（精细） | 14 / veryslow | 8 | 极限画质（只在最终交付用，很慢） |

`legacy` 的 `fps: 0` 表示「不覆盖项目 fps」——所以它渲出来的帧数与旧版完全一致，这是**向后兼容的硬证据**。

### 画质档（`--quality`）

画质只改 `deviceScaleFactor`，**不改任何布局**：同一份 HTML 只是采样更密，构图逐像素不变。

| `--quality` | 目标高度 | 1920×1080 项目上的 deviceScaleFactor | 输出分辨率 |
|---|---|---|---|
| `1080p` | 1080 | 1× | 1920 × 1080 |
| `2k` | 1440 | 1.333× | 2560 × 1440 |
| `4k` | 2160 | 2× | 3840 × 2160 |

> 项目画布不是 1080 高时，scale 按 `目标高度 / 项目高度` 换算。所以 `--quality` 是「输出多高」，
> 与项目本身写的是 1080 还是 720 无关。

### 自由组合

`--quality` 与 `--fps` 可任意组合，不被档位绑死：

```bash
node <skill>/scripts/render_video.mjs . --quality 2k --fps 60 --shutter 180 --workers 8
```

## 2. 质量 / 速度 / 体积的权衡

三个旋钮各管一件事，互不重叠：

| 旋钮 | 影响画面 | 影响体积 | 影响耗时 |
|---|---|---|---|
| `--quality`（分辨率） | 清晰度 | ↑↑ | ↑↑（像素平方） |
| `--fps`（帧率） | 流畅度（运动连贯） | ↑ | ↑（帧数线性） |
| `--shutter`（运动模糊） | 运动段不重影 | 几乎不变 | 只动帧才加（静帧跳过） |
| `--crf` / `--preset` | 编码失真 | ↑↓ | ↑（preset 越慢编码越久） |
| 截图模式（`png`/`png-fast`/`jpeg`） | 中间帧精度 | 中间帧体积 | **↑↑↑（最大杠杆）** |
| `--workers`（并行） | 无 | 无 | ↓（≈ 核数上限） |

要点：

- **中间帧编码是最大的耗时项。** 满幅照片/复杂合成的帧，PNG 编码能占 96% 的帧时间，且**与并发无关**。
  - `--png-fast`：无损，约 **4.4×** 提速（本机实测）。
  - `--jpeg --jpeg-quality 95`：约 **13×** 提速、体积约 **1/5**；q95 实测 PSNR 41.65 dB，
    **已低于 x264 crf18 自身的失真**，成片看不出来。图片型画面首选。
- **`preset` 只影响编码，不影响画质**：`medium`→`slow`/`veryslow` 是省体积换时间，不是变清晰。
  要明显提升清晰度请调 `--quality` 或降 `--crf`。
- **运动模糊不加体积**：它只改「动帧」的像素，静帧原样跳过，码率几乎不变，但观感提升明显。
- **`--workers` 只降时间**：不改变任何像素输出（帧是确定性的、按帧号分派）。

## 3. 快门运动模糊的原理

**不是 blur 滤镜，是线性光下的多样本积分。** 一个 180° 快门意味着曝光窗 = 半个帧周期：

```
openS = (shutter / 360) / fps        # 曝光窗长度（秒）
t_i   = t + openS * (i/K - 0.5)      # 在这一窗内均匀取 K 个采样时刻
```

对每个「动帧」，渲染器在这些时刻各截 **1 张**，共 K 张（默认 `--samples 8`），
再由 `blur_integrate.py` 在**线性光**下逐像素平均：

1. sRGB → 线性光（用 uint16 LUT，不是每像素 `pow`）；
2. 累加到 uint32；
3. 除以样本数、截回 uint16。

> 为什么必须在线性光下平均：sRGB 是伽马压缩过的，直接平均等于在非线性域做插值，
> 暗部会偏亮、亮部会偏暗，快速横移的边缘会出现「灰边」。线性光平均才是物理上正确的运动模糊。

### 采样数是自适应的

- 页面若导出 `window.__motion(t0, t1)`（返回这段时间内**屏幕最远移动了多少 px**），
  渲染器按每样本 `--motion-gap`（默认 24 px）反推需要的样本数，
  并夹在 `--samples-min`–`--samples-max`（默认 4–12）之间。
- **静帧（位移低于一格）只截 2 张就判定为 `hold` 并跳过积分** —— 所以纯静止的段落几乎不额外耗时。
- 反过来：**快动作 > 80 px/帧 若不开快门，会重影成串**（每帧是一个瞬间，人眼补不出来）。

### 跳过机制与硬切

被判定为 `hold` 的帧不写样本、直接沿用单张 —— 这些帧在元数据里记作 `still_frames`，
它们在成片里是干净的**硬切**（切场景的那一帧就该是硬的，不该被"糊"）。

## 4. 并行的原理

### 多浏览器进程级并行（`--workers N`）

`--workers N` 启动 **N 个相互独立的 Chromium 进程**，按**帧号**分派（worker i 负责 `frame % N == i`）。

> 关键：**不是**在一个浏览器里开 N 个 page。Chrome 的截图编码在一个浏览器进程内是串行的，
> 同浏览器开多 page 并发是**白挂的**（拿不到加速）。必须真的多进程。

日志会明确打印 `N 个**独立浏览器**进程级按帧步进` 以区别于旧行为。

### 断点续渲（`--resume`）

`--resume` 跳过已经落到磁盘的帧与已经积分的快门目录，**按 mtime 判定**（只有内容比上一次新才算数）。
4K 长片渲到一半挂掉时，重跑加 `--resume` 即可从断点继续，不重头来。

### 定期重启浏览器（`--recycle N`）

每渲 N 帧（默认 150）重启一次浏览器，**4K 长片防内存泄漏 / OOM**。

### 积分阶段也并行

`blur_integrate.py` 用多进程（默认 `min(核数-1, 12)`）跑积分，与截图阶段解耦，同样支持续算。

### 健壮性（挂死自愈）

- 每个 `setupPage` / 截图 / 启动 / 关闭都带超时（`HX_SHOT_TIMEOUT_MS`，默认 60s）；
- 单帧失败**最多重试 3 次**（`HX_FRAME_RETRY`），仍失败则**重启浏览器**再试；
- 全局看门狗：若 `SHOT_TIMEOUT + 45s` 内没有新帧产出，直接退出码 3 并**提示用 `--resume`**，
  而不是无限挂着。

## 5. 基准数据

基准工装会**合成一个复杂度可控的项目**（N 场 × 每秒动元素），在同机上多档位各渲一遍：

```bash
python <skill>/scripts/bench_render.py \
    --out .scratch/bench --scenes 2 --sec 1.0 --fps 30 \
    --configs legacy,draft,balanced,4k30,4k60 [--heavy] [--json]
```

- `fps` = 渲染帧数 / **截图耗时**（不含编码、不含积分）——看的是截图吞吐；
- **相对 `legacy` 的加速比才是重点**，绝对值随机器和帧内容变化很大；
- `--heavy` 打开「满幅渐变 + 多重 shadow + 半透明叠加」模拟高熵帧（照片型），
  这是 PNG 最慢、`--png-fast` / `--jpeg` 收益最大的场景。

> 工装会自动把每个档位的 `--fps` 同步到项目声明的总帧数（`layout._total.total_frames`）——
> 渲染器**采信声明帧数**（有意为之，避免帧数分歧导致 QC 假截断），所以工装必须同步改它，
> 否则 `4k60` 这种档位会按旧 fps 的帧数渲染、时长少一半，基准就不可比了。

### 5.1 本机量级（16 核 / Windows / Chrome / 纯 CSS 图形帧）

2 场 × 1.0s、1080p 项目、`--workers` 由档位决定：

| 档位 | 输出 | fps | 帧数 | 截图 s | 积分 s | 总 s | 帧/秒 | 加速比 | 体积 MB | 截图模式 |
|---|---|---|---|---|---|---|---|---|---|---|
| `legacy` | 1920×1080 | 30 | 60 | 21.4 | 0.0 | 23.6 | 2.8 | ×1.00 | 0.38 | png |
| `draft` | 1920×1080 | 30 | 60 | 6.2 | 0.0 | 8.0 | 9.7 | **×3.47** | 0.37 | png-fast |
| `balanced` | 1920×1080 | 30 | 60 | 16.6 | 7.1 | 27.5 | 3.6 | ×1.29 | 0.49 | png-fast |
| `4k30` | 3840×2160 | 30 | 60 | 16.9 | 5.9 | 26.4 | 3.5 | ×1.26 | 0.49 | png-fast |
| `4k60` | 3840×2160 | 60 | 120 | 25.4 | 8.8 | 37.5 | 4.7 | **×1.69** | 0.57 | png-fast |

**三个关键结论**：

1. **并行比分辨率更划算**：`4k30`（4× 像素）的截图吞吐（3.5 帧/秒）几乎追平 1080p 的 `balanced`（3.6 帧/秒）——
   因为 4K 档配了 8 个浏览器进程。**`legacy` 慢不是因为 1080p 贵，而是因为它是单浏览器串行**；
   换成多进程后，连 4K60 全片都只要 37.5 s。
2. **`draft` 是最强的加速杠杆**：无快门 + `png-fast` + 6 进程 = **9.7 帧/秒（×3.47）**。
   迭代期一律先用 `draft` 看节奏，定稿再上 `balanced` / `final`。
3. **快门几乎不加时间**：`hold` 静帧只截 2 张即跳过，代价只落在**动帧**上；
   它换来的运动段观感提升是成倍的 —— 这是默认档选 `balanced` 而非 `draft` 的原因。

> 数字是**本机量级**，随机器与帧内容（纯 CSS 图形 ↔ 满幅照片）能差 10× 以上。
> 换机器后重跑同一命令对比自己的基线，别把这张表当承诺值。

### 5.2 优化前后的根因与修法

这是「同速的前提下多拿到新能力」的依据（同一台机器、同一份 108 帧项目）：

| 指标 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| `balanced` 总耗时 | 70.4 s | **33.0 s** | 快 2.1× |
| 其中积分 + 清理 | 53.6 s | **8.5 s** | 快 6.3× |
| 逐帧并行加速比 | — | **10.2×**（12 进程） | 证明并行真有效 |
| 样本目录清理 | ~121 s（96 文件） | **0.62 s** | 见下 |

**三个根因与修法**：

1. **并行被"删除"拖垮**：旧实现把「删样本目录」放在积分的关键路径上，
   而本机对用户目录下的批量删除有实时扫描节流（96 个文件要 ~121 s）。
   → 把清理移出关键路径；改用**整目录 rename 到系统 Temp 再删**（0.084 s）。
2. **积分本身吃内存带宽**：逐像素 `pow` 线性化 + 大量中间数组。
   → 换成 **uint16 LUT + uint32 累加**，数值逐位不变（实测 PSNR 138.1 dB、最大差 0）。
3. **刚写完的 PNG 被扫描器占用**：保存偶发 `PermissionError`。
   → `_save_png` 带指数退避重试；探测灰度时用**步进抽样**（`rgb[::8,::8]`）不再 reshape 大数组。

**结论**：v2.0 的默认档不是「加了功能所以变慢」，而是在**同速的前提下多拿到了运动模糊、并行、断点续渲**。

## 6. 4K60 的硬件要求

4K60 的**原始工作量**是 1080p30 的 **4×（像素）× 2×（帧数）≈ 8×**，再叠加更大的 PNG 编码，约 **8–12×**。

但**实测墙钟差距远小于此**，因为 4K 档配了更多并行进程 —— 本机 `4k60`（120 帧 / 8 进程）总耗时 **37.5 s**，
而 1080p30 的 `balanced`（60 帧 / 6 进程）是 27.5 s，只差 **1.4×**。换句话说：
**并行能在很大程度上吃掉分辨率的代价**，4K60 不是「8 倍慢」，而是「多核机器上完全可做」。

> 读表提醒：基准里各档位的 `--workers` 不同（`legacy` 1 / `draft`·`balanced` 6 / 4K 8），
> 所以横向比总耗时是**端到端体验**，不是"同并行度下的纯分辨率代价"。要比纯分辨率代价，请固定 `--workers` 再跑。


| 资源 | 建议 | 说明 |
|---|---|---|
| CPU | **≥ 8 物理核**（`--workers 8` 才吃得满） | 截图是 CPU 密集；核数 = 并行上限 |
| 内存 | **≥ 16 GB**（长片 32 GB 更稳） | 每个 Chromium 进程数百分 MB–1 GB+ |
| 磁盘 | **SSD**，预留 **20–80 GB** | 4K PNG 单帧约 2–6 MB |
| 浏览器 | Chrome / Edge 任一 | 自动探测；无需额外安装 |

**4K 强制建议**：

- **中间帧用 `--jpeg --jpeg-quality 95` 或 `--png-fast`** —— 4K 精细 PNG 会把磁盘和编码时间吃干；
  q95 的失真低于 crf16 自身，看不出。
- **一定加 `--resume`** —— 4K60 长片中途失败概率不低，续渲省掉整轮重跑。
- **一定加 `--recycle 150`（或更小）** —— 4K 长片不重启浏览器容易 OOM。
- **`--workers` 别超过物理核数** —— 超了会互相抢 CPU 反而更慢。

```bash
# 4K60 终稿：JPEG 中间帧 + 续渲 + 定期重启
node <skill>/scripts/render_video.mjs . --profile final \
     --jpeg --jpeg-quality 95 --workers 8 --recycle 120 --resume \
     --audio audio/narration-full.mp3
```

## 7. 环境变量（渲染健壮性）

| 变量 | 默认 | 作用 |
|---|---|---|
| `HX_SHOT_TIMEOUT_MS` | 60000 | 单次截图/启动/关闭的超时；挂死机器可调小 |
| `HX_FRAME_RETRY` | 3 | 单帧最大重试次数（超过则重启浏览器） |

浏览器挂死的排查顺序：**调小 `HX_SHOT_TIMEOUT_MS` → 降 `--workers` → 加 `--resume` 重跑**。

## 8. 选档速查

| 你现在要干嘛 | 用什么 |
|---|---|
| 快速看节奏、迭代画面 | `--profile draft --preview N` |
| 出正式 1080p 成片 | `--profile balanced --audio …` |

| 验证本机性能 | `python scripts/bench_render.py --configs legacy,draft,balanced` |
